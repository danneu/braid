# Plan: sweep literal `(s)` pluralization out of user-facing CLI output

## Context

A review finding flagged `cli/src/ack.rs:93` for printing `acknowledged 1 alert(s)` -- a literal `(s)` suffix on a count that is always `>= 1` on that branch. The finding is real but is one instance of a wider anti-pattern: the codebase has **ten user-facing sites** that use `(s)` literals -- seven in format strings, two in Clap-derive `///` doc comments on `Commands::Add` and `AddArgs::disks` in `cli/src/main.rs` (which Clap renders into `braid --help` and `braid add --help` stdout), and one generated by Clap for the default `help` subcommand -- while already having standardized on inline ternaries (`if n == 1 { "" } else { "s" }` or `if n == 1 { "disk" } else { "disks" }`) at **fourteen other format-string sites** across `add.rs`, `remove.rs`, `replace.rs`, `doctor.rs`, and `preflight.rs`. Three files (`add.rs`, `doctor.rs`, `preflight.rs`) contain both styles internally.

This refactor finishes the convention by sweeping all `(s)` literals from user-facing output -- format strings and Clap help text alike -- to match the established style. No new helper is introduced: the project has shown deliberate preference for inlining the ternary at each format-string site (no `pluralize`/`Plural` helper exists), and adding 7 more sites keeps the codebase at ~21 inline ternaries, which the maintainers have signaled is acceptable. The two Clap doc-comment sites use a static plural (`disks`/`specs`) rather than a ternary because Clap help text is rendered once and the subcommand/arg always operates on `>=1` element by Clap definition (`num_args(1..)`). The generated Clap help subcommand is replaced with an explicit `help` subcommand that delegates back to Clap help rendering while using braid-owned prose. Outcome: every `(s)` hit under `cli/src/` is either Rust pattern-binding syntax or one of six enumerated internal comments (all non-user-facing, all explicitly listed in the Verification section); `grep -n '(s)' cli/src/main.rs` returns empty; and `braid --help` / `braid add --help` stdout (asserted in `cli/tests/root_check.rs`) contain no `(s)`.

**Test changes (decided in clarification):**

- `cli/src/doctor.rs:1574` -- assertion `"all 2 declared disk(s) present"` becomes `"all 2 declared disks present"` (2 != 1 takes plural branch).
- `cli/src/doctor.rs:1562` (doc-comment in the same test) -- references the old `(s)` text. Rewrite to a `(s)`-free description, e.g. `returns Ok with the healthy declared-disks summary message`. The new wording **must not contain `(s)`** -- the verification audit's allowed-residual list (step 1) does not include this site, so any new `(s)` here would be a refactor miss.
- `cli/src/preview.rs:550, 556, 577, 583` -- four arbitrary test-input strings hardcoded as `"pool has 1 missing device(s)"` / `"[warn] pool has 1 missing device(s)"`. **Out of scope:**

- Non-Clap source doc comments and inline comments that mention `(s)` in prose (e.g. `cli/src/remove.rs:657`, `cli/src/remove_missing.rs:1734`, `cli/src/add.rs:1604`, `cli/src/preflight.rs:327`, `cli/src/test_fixtures/add.rs:405`) -- these document internal functions/types and are not rendered into any user-facing output. Leave alone. **Distinction:** Clap-derive `///` doc comments on `Commands` / `*Args` structs in `cli/src/main.rs` ARE rendered into `--help` and so are in scope above; non-Clap `///` doc comments elsewhere stay out of scope.
- The NixOS module, scripts, docs, and NixOS VM tests -- exhaustive sweep found no `(s)` patterns there.
- Introducing a `pluralize(n, "noun", "nouns")` helper -- the project has chosen inline ternaries at 14 existing sites; adding a helper now would create a new convention competing with the established one. CLAUDE.md guidance ("Three similar lines is better than a premature abstraction") plus the project's revealed preference both point to inlining.
- Verb agreement at sites other than `doctor.rs:440`: e.g. `pool.rs:104`'s surrounding error has stable subjects, no verb agreement to fix.

## Reused convention

All 14 existing sites use one of two inline forms; the refactor matches them exactly, no new abstractions:

- **Suffix-only ternary** -- `if n == 1 { "" } else { "s" }`. Established at `add.rs:737`, `remove.rs:556`, `replace.rs:1642-1643`, `doctor.rs:622-623`, `preflight.rs:295-296`. Apply to `ack.rs:93`, `pool.rs:104`, `preflight.rs:31`, `preflight.rs:376`.
- **Full-word swap** -- `if n == 1 { "disk" } else { "disks" }`. Established at `remove.rs:862, 873, 875`, `replace.rs:1926, 1928`. Apply to `doctor.rs:391`.
- **Phrase swap** -- `if n == 1 { "is" } else { "are" }` at `add.rs:768`; extend the same idiom to swap `"disk has"` vs `"disks have"` together at `doctor.rs:440`.

No new helper, no new module, no new trait.

## Verification

1. **Static audit, broad sweep with allowed residuals.** Run `rg -n '\(s\)' cli/src --glob '*.rs'`. After the refactor, every hit must be either:
   - A Rust pattern binding or expression that happens to write `(s)` as syntax (`Ok(s)`, `Some(s)`, `Err(s)`, `|s|`, `style(s)`, `from_str(s)`, etc.) -- these are language tokens, not pluralization, and the broad sweep cannot avoid catching them. Or:
   - One of these six enumerated non-user-facing comments that this refactor explicitly leaves alone (each is an internal source/test/doc comment, never rendered to the user):
     - `cli/src/add.rs:1604` -- `// target(s). The Info note suppresses Preview::render's ...`
     - `cli/src/remove.rs:657` -- `/// Check that the surviving device(s) have enough space ...` (non-Clap doc comment on an internal helper)
     - `cli/src/preflight.rs:327` -- `/// allocations from the target device(s) being removed ...` (non-Clap doc comment on `check_raid1_relocation_space`)
     - `cli/src/remove_missing.rs:1734` -- `// Why it exists: regression guard against (a) the "-> X disk(s)" post-op ...` (test-rationale comment intentionally quoting the historical bug)
     - `cli/src/remove_missing.rs:1918` -- block-comment line referencing a PR title `"warn note(s) render before steps"` (quoted external string)
     - `cli/src/test_fixtures/add.rs:405` -- `/// mapper(s) in the post-add probe. Models the ...` (non-Clap doc comment on a test fixture)

   Any `(s)` hit outside this allowed set is a refactor miss. The previous "grep `(s)"` must return empty" check was incorrect: `remove_missing.rs:1734` legitimately matches that pattern because its rationale comment quotes the historical bug shape `"-> X disk(s)"`, and that comment is explicitly out of scope.

2. **Static check, Clap-derive help.** `grep -n '(s)' cli/src/main.rs` must return empty. `main.rs` is the only file with Clap derive structs and contains no Rust pattern bindings of the form `(s)` (verified -- the only two pre-refactor hits are at lines 25 and 167, both Clap-rendered doc comments). Do **not** apply a `grep -v '///'` filter at this step -- the original plan's filter is what masked those two sites in the first place.
3. **End-to-end check, rendered help text.** `cli/tests/root_check.rs` -- extend the file to assert:
   - `braid --help` stdout does not contain `"(s)"` (catches every Clap-rendered subcommand description in `Commands`).
   - `braid add --help` stdout does not contain `"(s)"` (catches positional-arg help on `AddArgs::disks` and any sibling flag help).
   - `braid help add` still works without root and does not contain `"(s)"` (guards the explicit help subcommand that replaces Clap's generated `(s)` wording).
   - These assertions can be folded into the existing `help_works_without_root` and `add_dry_run_flag_accepted` tests (just add an `assert!(!stdout.contains("(s)"), ...)` line), or added as sibling tests in the same style. Either is fine.
4. **Rust unit + integration tests.** `just test-rust` must pass. The known failing-then-fixed assertion is `doctor.rs:1574` (already accounted for). Watch for any other assertion this sweep destabilizes -- run the full suite to catch it; no other matches were found by an exhaustive grep of `cli/` for the literal output strings, but `cargo test` is the authoritative confirmation. The new `root_check.rs` assertions will also fail loudly until all `main.rs` doc-comment edits are applied -- this is the intended check, not a regression.
5. **NixOS VM tests.** `just test-vm` should pass unchanged. The exhaustive search of `tests/**/*.py` found no greps for any of the seven cited literal output strings, so no VM-test brittleness is expected. If a regression surfaces, the brittleness is the test's, not the refactor's -- update the test to grep for the new prose.
6. **Spot-check end-to-end behavior** in a NixOS VM or via the existing CLI tests:
   - `braid --help` lists `Add disks to the pool` for the `add` subcommand (not `Add disk(s)...`).
   - `braid add --help` shows `Disk specs: NAME=...` for the positional argument (not `Disk spec(s):...`).
   - `braid ack` after a single latched cause prints `acknowledged 1 alert` (not `1 alert(s)`).
   - `braid doctor` on a healthy 1-disk pool prints `all 1 declared disk present`; on a healthy 2-disk pool prints `all 2 declared disks present`.
   - `braid add disk1` (single-disk add) emits an inhibitor description of `"adding disks to pool"` (visible via `systemd-inhibit --list` during the add). Static plural is intentional.
   - `braid add` against a locked pool with one stale member prints `pool.json lists 1 member: <name>`.
7. **Commit hygiene.** Single commit, Conventional Commits style with lowercase first line, e.g. `refactor(cli): drop literal "(s)" suffix in user-facing output`.

## Non-goals

- No changes to behavior, exit codes, error variants, or message semantics. Only the rendered noun/verb form changes.
- No new unit-test coverage of formatting logic. The two `root_check.rs` assertions added in verification step 3 are structural ("rendered help contains no `(s)`"), not behavioral; they exist purely to prevent reintroduction. The existing `doctor.rs:1574` assertion update is the only behavioral test change.
- No backwards-compatibility shims (braid is unreleased software).
