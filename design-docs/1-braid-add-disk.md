# Design: braid-add-disk

## Purpose

One-shot imperative CLI tool that formats a new physical disk and adds it to the braid pool. This is the only destructive action in the system — `nixos-rebuild switch` never formats or destroys data.

## Usage

```
$ sudo braid-add-disk /dev/disk/by-id/ata-Toshiba_MN07_XXXX
```

## Config-first workflow

See [docs/principles.md](../docs/principles.md) for the config-first principle and [docs/decisions/config-first-workflow.md](../docs/decisions/config-first-workflow.md) for detailed rationale.

The workflow is:

1. User plugs in a new disk
2. Finds its by-id path: `ls /dev/disk/by-id/`
3. Adds it to `braid.disks` in NixOS config
4. `sudo nixos-rebuild switch` — module writes `/etc/braid/config.json`, creates LUKS entries (which fail gracefully — disk isn't formatted yet)
5. `sudo braid-add-disk /dev/disk/by-id/ata-NewDisk` — script reads config, verifies disk is expected, formats LUKS, creates/extends btrfs pool
6. Pool is immediately available. Next reboot auto-unlocks.

## Behavior by pool state

### No pool exists yet (first disk)

1. Validate the block device exists, is a by-id path, and is in `braid.disks`
2. Validate the device is not already LUKS-formatted
3. Print disk info (model, size, serial) via `lsblk`
4. Prompt for LUKS passphrase twice (confirm match)
5. `cryptsetup luksFormat` the device
6. `cryptsetup luksOpen` with mapper name derived from by-id basename
7. `mkfs.btrfs` (single device, no RAID1 — can't with 1 drive)
8. Mount at the configured mount point
9. Print summary: "Done. This disk will auto-unlock on next reboot."
10. Warn: "No redundancy yet — add a second disk for RAID1 protection."

### Pool exists with 1 device (second disk — enables RAID1)

1. Validate the block device exists, is a by-id path, and is in `braid.disks`
2. Validate the device is not already LUKS-formatted
3. Print disk info
4. Prompt for LUKS passphrase once
5. **Verify passphrase** by opening an existing LUKS device from the pool — if it fails, refuse to proceed ("Passphrase doesn't match your existing disks")
6. `cryptsetup luksFormat` the new device with the verified passphrase
7. `cryptsetup luksOpen` with mapper name derived from by-id basename
8. `btrfs device add /dev/mapper/<name> /mnt/storage`
9. `btrfs balance start -dconvert=raid1 -mconvert=raid1 /mnt/storage`
10. Print summary: "Done. This disk will auto-unlock on next reboot."

### Pool exists with 2+ devices (third+ disk)

Same as above. `btrfs device add` + `balance -dconvert=raid1` to redistribute across all devices.

## Design decisions

### Passphrase handling

- **First disk:** prompt twice, confirm match. Standard new-passphrase flow.
- **Subsequent disks:** prompt once, then verify against an existing LUKS device in the pool. This enforces all disks use the same passphrase without storing it anywhere. The `braid unlock` UX depends on this — one passphrase unlocks all drives.
- **How verification works:** the script reads which devices are in the btrfs pool (`btrfs fi show /mnt/storage`), picks one, tries `cryptsetup luksOpen --test-passphrase` against it. If it fails, the user mistyped or used a different passphrase.

### LUKS mapper naming

Both the module and script derive mapper names from the by-id basename. `/dev/disk/by-id/ata-Toshiba_MN07_XXXX` → mapper name `ata-Toshiba_MN07_XXXX`. This is deterministic and requires no coordination — both derive from the same source.

The mapper name doesn't matter for btrfs — it finds all devices by UUID internally. The naming is only for LUKS open/close.

### Pool detection

- The script reads `/etc/braid/config.json` (generated by the NixOS module) for mount point and expected disks.
- If the mount point is a mounted btrfs filesystem: pool exists. `btrfs fi show` gives device count.
- If the mount point is not mounted: no pool yet (first disk path).
- Live system state is still used for pool presence detection and safety checks.

### Safety checks

The script must refuse to proceed if:
- The disk path is not a `/dev/disk/by-id/` path
- The disk is not in `braid.disks` (config guard)
- The device is already LUKS-formatted (`cryptsetup isLuks`)
- The device has a recognized filesystem (`blkid`)
- The device is currently mounted
- The user doesn't type the exact confirmation phrase

### Config guard

The script refuses to format disks not listed in `braid.disks`. This prevents config drift (disk formatted but not in NixOS config) and ensures pool unlock works automatically. The error message tells the user exactly what to add and which commands to run.

### Confirmation UX

```
WARNING: This will PERMANENTLY ERASE all data on:
  /dev/disk/by-id/ata-Toshiba_MN07_XXXX
  Model: Toshiba MN07ACA12T
  Size:  12 TB
  Serial: XXXXXXXXXXXX

It will be LUKS-encrypted and added to the btrfs pool at /mnt/storage.

Type 'erase this disk' to confirm:
```

```

```

## Implementation

Bash script, packaged via `pkgs.writeShellApplication`:

```nix
braid-add-disk = pkgs.writeShellApplication {
  name = "braid-add-disk";
  runtimeInputs = [ pkgs.cryptsetup pkgs.btrfs-progs pkgs.util-linux pkgs.jq ];
  text = builtins.readFile ./braid-add-disk.sh;
};
```

### Dependencies in PATH

- `cryptsetup` — LUKS format/open/test-passphrase
- `btrfs` — mkfs, device add, balance, fi show
- `lsblk` — disk info display
- `blkid` — existing filesystem detection
- `jq` — read `/etc/braid/config.json`

## Relationship to the NixOS module

The module is the source of truth. The script reads from it:

- **Module** declares disks in `braid.disks`, exports `/etc/braid/config.json`, sets up pool unlock/mount/samba
- **Script** reads config, validates disk is expected, runs destructive one-shot operations

They agree on:
- Mount point: from config
- Disk identification: `/dev/disk/by-id/` paths
- LUKS mapper naming: derived from by-id basename

The module never calls the script. The script refuses to operate on disks not in the module config.

## Testing

The script can be tested in NixOS VM tests with virtual drives. The test provides `/etc/braid/config.json` manually (without importing the module) and runs through:
1. First disk (creates pool)
2. Second disk (converts to RAID1)
3. Third disk (expands pool)
4. Validation errors (non-by-id path, unconfigured disk, already-in-pool)
5. Crash recovery (LUKS with no filesystem)
6. Unmounted pool guard
